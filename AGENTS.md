# Muesli: notes for coding agents

Muesli is an on-device meeting transcriber for **macOS and Windows**. It captures the microphone ("You") and system audio ("Others"), transcribes with Whisper locally, writes Markdown and JSON transcripts, and exposes them to AI assistants through an MCP server (`muesli-mcp`, stdio).

## One app, two platforms
- **macOS and Windows ship the same Tauri app** (`apps/desktop`), with the same web UI (`ui/`) and the same Rust crates, in one Cargo workspace at the repo root. The UI looks the same on both (no per-platform stylesheets): only the title bar (macOS draws a strip under its overlay title bar, Windows colours its native one) and the Settings shortcut (⌘, / Ctrl+,) differ, and platform words come from `PlatformWords`. A feature is done when it works on both, or when `docs/PLATFORMS.md` records why one platform differs.
- The SwiftUI app is retired. `macos/` stays in the repository, untouched and no longer built, until the maintainer has verified the Tauri app on a real Mac; then it is deleted. Never add to it.
- **Ports and adapters.** The core never calls the OS. Every OS service is a trait (a port) in `crates/core/src/ports.rs`: `Clock`, `MicCapture`, `SystemAudioCapture`, `MeetingDetector`, `Notifier`, `Permissions`, `Tray`, `Trash`, `PlatformPaths`, `LoginItem`, bundled in `Platform` with the platform's words (`PlatformWords`: Trash/Recycle Bin, Finder/Explorer, Mac/PC…). `Updater` (Muesli's own updates) is a port too, but the shell provides it (`apps/desktop/src/updater.rs`, `tauri-plugin-updater`, the same on both platforms) and hands it to the engine in `Options`; debug builds have none and never check.
  - Adapters: `platform-macos` (objc2: EventKit, UNUserNotificationCenter, AVFoundation, NSFileManager, SMAppService, Core Audio), `platform-windows` (WASAPI sessions, toasts, registry), `platform-common` (what both share through portable crates: clock, folders, trash, Teams scan, cpal capture), `platform-fake` (every port, drivable, builds everywhere).
  - `port-contracts`: one test suite per port. `tests/fakes.rs` runs them against the fakes everywhere; `tests/native.rs` against the native adapters on their own OS.
  - A new OS call means: a port method, a fake, a contract and both native adapters.
- **The engine decides, the UI renders.** `crates/engine` (`muesli-engine`) holds the behaviour: detection prompts, transcribing, the end-of-call question and its 5-minute timeout, imports, the main window, Settings and setup. Each window asks for its view state (`Engine::view`) and sends `Intent`s; the tray menu is `Engine::menu`. The UI never decides anything a test should check; platform words come from the view. `Host` is what the shell does for the engine (windows, pickers, reveal, quit); `SpeechModel` wraps the model download, whisper.cpp, a voice activity detector per live stream and the echo canceller. Echo cancellation: `EchoStage` in `crates/core/src/aec.rs` (alignment, passthrough, fail-safe; tested with `StandInCanceller`), LocalVQE in `crates/aec` (a git submodule, built with CMake as a shared library and opened at run time, never linked: its ggml would clash with whisper.cpp's).
- **Live audio.** Capture callbacks only hand samples to a worker (`crates/engine/src/live.rs`); it owns one `Segmenter` per speaker (`crates/core/src/segmenter.rs`: pause-based blocks, REQUIREMENTS A10b) and sends blocks to the single transcribing thread, which times Whisper so blocks grow when it falls behind (`Pacer`). File imports keep fixed 30 s chunks.
- **The simulator.** `apps/sim` (`muesli-sim`) runs the real engine with the fakes and the real `ui/` pages in a browser, in either skin, with scenarios from `fixtures/scenarios/`. The UI tests (`apps/sim/tests`, Playwright) drive it. Never shipped.
- Shared files: `config.json`, `state.json`, `meetings/*.json`, `vocabulary.json` (written by the app and `muesli-mcp`, so read on use, never cached), transcripts, and the nine MCP tools. `fixtures/` freezes the formats (`fixtures/core`) and MCP replies (`fixtures/mcp`), checked by `crates/core/tests/golden.rs` and `crates/mcp/tests/contract.rs`; edit them by hand, on purpose, when a format or reply changes. JSON and MCP values (`recording`, …) keep their values even where the UI says "transcribing".

## Rules
- Logic goes in the core crates (`crates/core` for data and rules, `crates/engine` for behaviour) with tests against the fakes. `apps/desktop` stays thin: adapters for the tray, windows and dialogs, and wiring.
- Use libraries for the hard parts (resampling: `rubato`; audio devices: `cpal`; atomic writes: `tempfile`; ids: `uuid`; objc2 for Apple frameworks). Do not hand-roll replacements.
- Audio is never written to disk. The only network requests are the model downloads (Whisper and voice activity) and the update check to GitHub (with the update download it finds). The echo cancellation model is bundled with the app (`scripts/fetch-aec-model.py` at build time), never downloaded by it.
- Transcribing must be impossible while no model is ready, and nothing may prompt for a permission outside the setup screen and Settings (the "Allow…" buttons).
- The UI says "transcribe / transcribing", never "record".
- Platform differences are documented in `docs/PLATFORMS.md`, split into what the platform imposes (for example: Windows has no system calendar, needs no system-audio permission, and its tray icons take no file drops) and what is simply not done yet. Before calling something impossible on a platform, check it and record the reason there.
- Follow `assets/brand/BRAND.md` for logo, colours and tone (no coloured accent stripes on card edges: use tints, dots or badges). `assets/brand` is the only source for icons: `apps/desktop/icons/` and `ui/brand/` are generated by `scripts/sync-icons.py`, never edited.
- Nothing platform-specific lives at the repo root. Shared things go in `assets/`, `fixtures/`, `scripts/` or `docs/`.
- `plugin/` is a Claude plugin (installed from this repo; its `server/muesli-mcp.js` launcher starts `muesli-mcp` on both platforms, and the app writes `mcp-path` for it); keep it in step with `muesli-mcp` (tool list in its skill and README) and run `python3 scripts/sync-plugin.py` after a version bump. `plugin/LICENSE`, `plugin/icon.png` and the plugin version are generated by that script.
- Keep `CHANGELOG.md` current: every change a user can see or use gets a line under `[Unreleased]` (Added, Changed, Fixed, Removed), in plain end-user words; no refactors or internals. The Release workflow turns `[Unreleased]` into the released version with its date (`scripts/release.py`); do not bump the version by hand.
- Keep `README.md` (users), `CONTRIBUTING.md` (developers), `docs/REQUIREMENTS.md`, `docs/PLATFORMS.md` and this file current with every change.

## Verifying
- `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace` at the repo root. On macOS and Windows that builds LocalVQE: the submodule must be checked out (`git submodule update --init --recursive`) and the model fetched (`python3 scripts/fetch-aec-model.py`). On Linux the whole workspace builds (the app with the fakes; it needs WebKitGTK), but `platform-macos` and `platform-windows` compile to nothing there.
- UI: `cargo build -p muesli-sim`, then in `apps/sim`: `npm ci`, `npx playwright install chromium`, `node --test tests/*.test.mjs`.
- On a Mac or PC also `cargo test -p muesli-port-contracts --test native` (and `-- --ignored` for the contracts that need a device, a person or change the machine).
- CI: **Tests** (Rust on macOS, Windows, Linux; UI tests; generated files) runs on every push and pull request; still run the tests locally before pushing. **Release** (`release.yml`, by hand from `main`): runs **Tests** (`tests.yml`) first, then tags the version in `Cargo.toml`, builds signed installers and updater bundles into a draft GitHub release titled `v<version>`, checks the draft has `latest.json`, then moves `main` to the next patch version; `test_build` only builds installers; `rebuild=<version>` builds an existing tag again into its release. Only the maintainer starts it; never create tags or releases yourself. See CONTRIBUTING.md, "Releasing".
- Say plainly what was not built or run on macOS or Windows. `docs/PLATFORMS.md` section 3 records what has been verified on real machines.
